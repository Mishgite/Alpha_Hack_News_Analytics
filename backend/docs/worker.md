# Воркер

Отдельный процесс для RSS, котировок, разметки и AI-разборов. HTTP-сервер запускается отдельно.

## Запуск в PyCharm

1. Настроить Python 3.12, окружение `backend/app/.venv` и PostgreSQL по [инструкции](database-setup.md)
2. Выполнить `app/infrastructure/database/init_db.py` через **Run**
3. В `app/.env` указать ключ и адрес API хакатона: `LLM_API_KEY`, `LLM_BASE_URL`, модели `LLM_MODEL_TAGGING`, `LLM_MODEL_CONTEXT`, `LLM_MODEL_ANALYSIS`; пример находится в `app/.env.example`
4. Если подготовленные отчёты уже находятся в `backend/data/reports_processed`, выполнить `app/import_reports.py` через **Run**; оригиналы PDF хранить в `backend/data/reports`
5. Выполнить `app/server.py` через **Run**
6. Выполнить `app/worker.py` через **Run** в отдельной конфигурации
7. В Swagger пройти демовход и проверить `GET /api/status`: `worker_alive=true`, `analysis_available=true`

Один проход вместо постоянной работы: **Run → Edit Configurations → Parameters → `--once`**. Код завершения 0 означает успешный проход, 1 означает ошибку одного из этапов. Ошибка указывается в логах без секретов.

Ctrl+C прекращает новые итерации и ожидает завершения текущих операций. Жёсткая остановка может прервать запрос к провайдеру. Второй воркер для той же БД не запускается благодаря блокировке PostgreSQL.

## Процессы

- RSS: Банк России, до 30 записей раз в 15 минут; `NewsPipeline` сохраняет новости без дублей
- Разметка: одна ожидающая новость, затем пауза 5 минут; `NewsTagger` сохраняет проверенные признаки
- Профили: одна новая или изменённая компания пользователей, затем пауза 2 минуты; ошибки повторяются не чаще раза в час
- PDF: при запуске импортируются подготовленные текстовые блоки; сомнительные блоки исключаются, номер страницы и сведения OCR сохраняются
- MOEX: котировки обновляются каждые 15 минут; при ошибке предыдущий срез остаётся доступен с признаком `stale`
- AI: очередь проверяется каждые 5 секунд; агент строит план, ищет по отчётам, готовит разбор, проверяет цитаты и выводы, при необходимости делает одну коррекцию
- Состояние: воркер обновляет heartbeat каждые 15 секунд; API считает его недоступным через 60 секунд без обновления

Операции выполняются в независимых циклах. Парсер и синхронные сервисы работают в потоках, сетевые запросы агента асинхронные. Транзакции БД не остаются открытыми на время LLM-запроса.

Обычная ошибка AI-задания даёт `failed`. После аварии процесса задание можно забрать заново после истечения lease, максимум три попытки. Некорректный результат разметки требует `NewsService.retry_tagging(news_id)`; при недоступности модели или исчерпанном бюджете новости остаются в очереди.

## Бюджет

- Общий бюджет команды: 500 ₽ в день, обновление в 03:00 МСК по уточнению организаторов
- Перед платным запросом проверяется `/key/info` на том же шлюзе, без `/v1` в пути
- При остатке 50 ₽ или меньше новые вызовы прекращаются; порог задаёт `LLM_BUDGET_RESERVE_RUB`
- Если остаток проверить не удалось, платный вызов не выполняется
- Дополнительный локальный предел: `LLM_DAILY_REQUEST_LIMIT=30` попыток за сутки UTC в одной БД, включая ошибки провайдера
- `LLM_MAX_OUTPUT_TOKENS=8192` ограничивает длину ответа; количество токенов и статус сохраняются в `llm_usage`
- Для GLM передаётся `reasoning_effort="low"`; автоматический повтор обрезанного ответа отключён; параметр описан в [документации Z.ai](https://docs.z.ai/api-reference/llm/chat-completion)
- Последний проверенный бюджет доступен в `GET /api/status`, поле `llm_budget` с временем проверки

Локальный счётчик не учитывает вызовы из других баз команды. Общий денежный предел контролирует шлюз; проверка остатка не резервирует деньги и не исключает параллельные расходы других участников. Стоимость отдельного вызова в рублях не выдумывается из числа токенов.

Готовые новости и неизменившиеся профили повторно не размечаются. Повторный AI-разбор использует кеш. Один новый разбор требует обычно 3 вызова модели, с коррекцией до 5; уточняющий ответ требует 2. Постоянный запуск воркера расходует бюджет на новые данные.

Запросы передают города группами по региону: все названия, переводы и коды сохранены, название региона указано один раз на группу. JSON передаётся без лишних пробелов. Проверяющий агент получает ID отрывков вместо повторяющихся цитат; сами отрывки и полный доступный контекст источников остаются в запросе. В API и БД сохраняются обычные результаты с дословными цитатами.

## Настройки

Параметр `--config C:/path/worker.json` задаёт JSON с полями `WorkerSettings`; остальные поля получают значения по умолчанию.

```json
{
  "sources": [{"code": "cbr", "url": "https://www.cbr.ru/rss/RssPress", "limit": 30, "full_text": false}],
  "fetch_interval": 900,
  "tagging_interval": 300,
  "tagging_batch": 1,
  "analysis_interval": 5,
  "analysis_timeout": 900,
  "profile_batch": 1,
  "profile_interval": 120,
  "market_enabled": true,
  "market_interval": 900
}
```

Интервалы указаны в секундах. `sources: []` отключает RSS, `market_enabled: false` отключает MOEX. `reports_directory` позволяет заменить каталог подготовленных PDF.

`full_text: false` сохраняет доступный текст RSS. При `true` парсер дополнительно загружает страницы статей, максимум две одновременно. Недоступный полный текст заменяется RSS-анонсом; агент получает только реально сохранённый текст.

## Импорт отчётов

`app/import_reports.py` принимает `--directory` с каталогом результатов подготовки: подпапки с `manifest.json` и JSON страниц. Это не скрипт OCR. Для работы нужен уже подготовленный набор из `backend/data/reports_processed`.

Повтор одинакового содержимого сохраняет прежние ID фрагментов. Изменённая обработка создаёт новую версию, поэтому старые цитаты остаются доступны. Агент выбирает ID подтверждающих отрывков, сервер подставляет дословный текст; затем модель отдельно проверяет, подтверждает ли он вывод. Исходные файлы не удаляются. Папка `newspaper_parser` в этот процесс не подключена.

Без подготовленных отчётов воркер продолжает работу; агент обязан указать отсутствие подтверждённой позиции банка. Файлы из `backend/data` и ключи не передаются через Git.
