# Настройка и запуск

Python **3.12**, PostgreSQL **17.x**, Node.js **22.12+**

## 1. Окружение Python

1. Открыть в PyCharm корень проекта с папками `backend`, `frontend` и `.run`
2. **Settings → Python Interpreter → Add Interpreter → Add Local Interpreter → Virtualenv**
3. Выбрать Python 3.12, создать окружение в **`backend/app/.venv`**, без наследования системных пакетов
4. Выбрать созданное окружение интерпретатором проекта
5. Для папки `backend`: **Mark Directory as → Sources Root**
6. Открыть `backend/app/requirements.txt`, выбрать **Install requirements**

Если уведомления установки нет: в терминале с активированным окружением выполнить `python -m pip install -r backend/app/requirements.txt` из корня проекта

## 2. PostgreSQL

1. Установить PostgreSQL 17, если его ещё нет: [установщик](https://www.postgresql.org/download/windows/), [инструкция EDB](https://www.enterprisedb.com/docs/supported-open-source/postgresql/installing/windows/)
2. При установке выбрать **PostgreSQL Server**, **pgAdmin 4**, **Command Line Tools**; порт `5432`, каталог данных вне проекта; сохранить пароль пользователя `postgres`
3. Открыть pgAdmin, подключиться к локальному серверу. Если подключения нет: **Servers → Register → Server**, имя любое; **Connection**: host `127.0.0.1`, port `5432`, maintenance database `postgres`, username `postgres`, установленный пароль
4. **Databases → Create → Database**: имя `alfa_news`, owner `postgres`

Вместо шага 4 можно выполнить в PowerShell:

```powershell
& "C:\Program Files\PostgreSQL\17\bin\psql.exe" -X -h 127.0.0.1 -p 5432 -U postgres -d postgres -W -v ON_ERROR_STOP=1 -c "CREATE DATABASE alfa_news;"
```

5. Скопировать `backend/app/.env.example` в `backend/app/.env`
6. В `DATABASE_URL` заменить `replace_with_local_password` на пароль PostgreSQL; проверить пользователя, порт и имя базы. Спецсимволы пароля кодируются для URL, например `@` как `%40`, `#` как `%23`, `%` как `%25`
7. Открыть `backend/app/infrastructure/database/init_db.py`, выбрать **Run**. Ожидаемый результат: `Reaction trigger: OK` и `OK`

Повторный запуск проверяет схему и синхронизирует справочник тем, данные сохраняются. Изменения существующих таблиц автоматически не применяются. В pgAdmin таблицы находятся в **alfa_news → Schemas → public → Tables**

## 3. Модель

В `backend/app/.env` указать `LLM_API_KEY` команды. `LLM_BASE_URL` и `LLM_MODEL_TAGGING`, `LLM_MODEL_CONTEXT`, `LLM_MODEL_ANALYSIS` взять из `.env.example`: используются модели API хакатона

- `LLM_DAILY_REQUEST_LIMIT=100`: предел попыток за сутки UTC в одной БД, включая ошибки
- `LLM_BUDGET_RESERVE_RUB=50`: остановка новых вызовов при остатке общего бюджета 50 ₽ или меньше
- `LLM_MAX_OUTPUT_TOKENS=8192`: предел ответа модели

При бюджете 500 ₽ резерв 350 ₽ оставляет ориентир 150 ₽ на проверки. Это не строгая квота расходов: другие компьютеры используют тот же ключ, а проверка остатка не резервирует деньги. Перед платным вызовом проверяется остаток на шлюзе; если проверка недоступна, вызов отменяется

При обновлении существующей локальной БД запустить `app/group_news.py` через Run, чтобы создать таблицу событий и сгруппировать сохранённые новости. Docker bootstrap делает это автоматически. Платных запросов нет. [Описание группировки](news-events.md)

## 4. Компании из CSV

1. Получить у команды исходные **`df_Uid_data_hack.csv`**, **`df_Fid_Uid_link_hack.csv`**, **`df_Uid_payment_hack.csv`**
2. Положить все три файла в **`backend/data/companies/`**
3. Для той же выборки из 50 компаний получить у команды **`selection.txt`**, положить рядом с CSV. Формат: один ID вида `U_123` в строке, без заголовка. Файл содержит только выбор ID; все данные читаются из CSV
4. Открыть **`backend/app/import_companies.py`**, выбрать **Run**, дождаться `Профили: 50/50` и завершения с кодом `0`

Скрипт проверяет весь CSV, исключает некорректные строки, нулевые байты и все повторы ID. Загружает выбранные 50 компаний, последовательно вызывает модель для определения тем, проверяет результат и сохраняет его в БД. Факты о компании берутся из CSV: модель не заменяет город, регион, выручку или банковские продукты своими предположениями

Без `selection.txt` выбираются 50 компаний с выручкой более 15 млрд рублей и разнообразием отраслей и регионов; их ID сохраняются в этот файл после импорта CSV, до первого платного запроса. После успешной разметки все 50 появляются в выборе компании на фронте. Предыдущая выборка заменяется только после завершения всей обработки; остальные записи БД не удаляются

Порог применяется к `REVENUE_COMPANY > 15000000000` без изменения исходного числа и без суммирования по `GROUP_ID`

Дополнительные CSV дают агрегаты связей и концентрации платежей. Они относятся только к предоставленной выборке, не доказывают владение компанией или полноту её оборотов. Место по выручке рассчитывается внутри группы ОКВЭД в наборе, не является долей рынка. Физлица модели не передаются

Повторный запуск пропускает готовые версии профилей без платного запроса. При ошибке процесс останавливается, уже сохранённые результаты остаются в БД; после устранения причины повторить **Run**. Воркер использует то же состояние разметки и не обрабатывает готовые версии заново

Существующие компании с тем же ID сохраняются без перезаписи исходных полей. Для обновлённого датасета сначала требуется явно обновить профиль через `ProfileService.save_company()`; обычный импорт не затирает изменения команды

Дополнительные параметры в **Run → Edit Configurations → Parameters**:

- `--check`: только проверка CSV и выборки, без БД и модели
- `--limit 20`: другая численность выборки
- `--min-revenue 0`: отключить порог крупного бизнеса для отдельного эксперимента; для сдачи оставить 15 млрд
- `--ids C:/path/selection.txt`: другой список ID; его длина должна совпадать с `--limit`
- `--source C:/path/df_Uid_data_hack.csv`: другой путь к исходному CSV
- `--skip-tagging`: только импорт CSV, без модели и смены выборки интерфейса
- `--all --skip-tagging`: импорт всех корректных строк без платной массовой разметки

Отчёт и отклонённые строки: `backend/data/import_results/<запуск>/summary.json` и `rejected.csv`. CSV, список ID и отчёты исключены из Git. Файлы компаний передаются внутри команды отдельно

## 5. Новости и отчёты

1. Запустить **`backend/app/import_news.py`** через **Run**. Будут загружены 104 реальные публикации из `backend/data/examples/recent-news-2026-10-25.json`, без вызова модели
2. Получить у команды каталог **`reports_processed`** с `manifest.json` и JSON страниц, положить в `backend/data/reports_processed`
3. Запустить **`backend/app/import_reports.py`** через **Run**, проверить отсутствие ошибок

Повторный импорт не создаёт дубли. `import_reports.py` читает подготовленные тексты, не распознаёт PDF. Исходные PDF лежат локально в `backend/data/reports`. Без отчётов лента работает, но AI не сможет сослаться на отсутствующие материалы банка

У новостей сохранены ссылки, даты и пересказы, без копий полных статей. Исходные 7 размечены моделью, следующие 93 ассистентом, деловой масштаб этих 100 дополнен моделью; последние 4 размечены ассистентом. Поля `annotation_method`, `review_basis`, `summary_review`, `published_precision` описывают происхождение каждой записи. `confidence=1` в ручной подготовке означает включение тега, не измеренную вероятность. Это примеры для демонстрации, не экспертная обучающая выборка

Даты не сдвигаются при импорте. Для старых примеров выбрать период через **Фильтр** над лентой; для свежих публикаций нужен воркер

Параметры `import_news.py`: `--limit 3`, `--file путь.json`; `--refresh-features` явно заменяет готовые признаки из JSON; `--tag` платно размечает записи без признаков и сохраняет результат в JSON

Если исходных материалов пока нет, **`backend/app/demo_data.py`** создаёт отдельную синтетическую компанию `demo-api-company` и три тестовые новости без вызова модели

## 6. Фронтенд

1. Выбрать установленный Node.js в настройках PyCharm
2. В терминале из папки `frontend` выполнить `npm ci`. При блокировке `npm.ps1` использовать `npm.cmd ci`
3. Скопировать `frontend/.env.example` в `frontend/.env.local`
4. Оставить `VITE_API_URL=http://127.0.0.1:8000`, без `/api` в конце
5. В `backend/app/.env` оставить `API_DEMO_ENABLED=true` и адреса `http://127.0.0.1:5173`, `http://localhost:5173` в `API_CORS_ORIGINS`

После изменения переменных перезапустить соответствующий процесс. Ключ LLM хранится только в бэкенде

## 7. Запуск приложения

В PyCharm выбрать **Все сервисы** и нажать **Run**: запускаются API, фронтенд и воркер. Открыть **http://127.0.0.1:5173**

**Без воркера** запускает API и фронт: работают сохранённая лента, профиль, реакции и готовые разборы. Новые разборы требуют воркер. Уточняющие вопросы к готовому разбору обращаются к модели через API и расходуют бюджет даже без воркера

Отдельные конфигурации: **Backend**, **Frontend**, **Worker**, **Компании - импорт 50**, **БД - создать таблицы**, **БД - проверить**. Файлы находятся в `.run`; используется интерпретатор проекта

Если общие конфигурации недоступны:

1. Открыть `backend/app/server.py`, выбрать **Run**
2. Из папки `frontend` выполнить `npm run dev`
3. Открыть `backend/app/worker.py`, выбрать **Run**

Перед повторным запуском остановить прежние процессы. PostgreSQL работает как системная служба и запускается отдельно

### Что выполняет воркер

Схемы: [сбор и разметка новостей](architecture.md#обработка-новостей), [выполнение AI-задания](architecture.md#ai-разбор)

- Каждые 15 минут: RSS Банка России, ТАСС и Интерфакса; котировки MOEX. Для двух агентств выбираются экономические рубрики, до 10 записей из каждого
- Каждые 5 минут: разметка одной ожидающей новости
- Каждые 2 минуты: разметка одной изменённой компании пользователей
- Каждые 5 секунд: очередь новых AI-разборов
- При запуске: импорт подготовленных отчётов

Для других источников передать воркеру `--config C:/path/worker.json`. Поля и значения по умолчанию: [WorkerSettings](../app/schemas/worker.py)

```json
{
  "sources": [{"code": "cbr", "url": "https://www.cbr.ru/rss/RssPress", "limit": 30, "full_text": false}],
  "fetch_interval": 900,
  "tagging_interval": 300,
  "tagging_batch": 1,
  "profile_interval": 120,
  "profile_batch": 1,
  "market_interval": 900,
  "market_enabled": true
}
```

Интервалы в секундах. `sources: []` отключает RSS, `market_enabled: false` отключает MOEX. `categories` ограничивает записи рубриками RSS, пустой список допускает все рубрики. `full_text: true` включает загрузку статьи; если она недоступна, сохраняется анонс RSS. Ошибка отдельного источника не останавливает остальные циклы. На одну БД запускается один воркер

## 8. Проверка перед демонстрацией

1. Повторно запустить `init_db.py`: ожидается `OK`
2. Открыть **http://127.0.0.1:8000/health** и **http://127.0.0.1:8000/docs**
3. Войти с компанией, открыть ленту; сменить компанию на другую отрасль при той же роли и периоде, сравнить подборки
4. Изменить темы над лентой, проверить сохранение после обновления страницы
5. Открыть AI-разбор, дождаться результата, проверить источники и задать уточняющий вопрос
6. Открыть биржевой обзор, проверить поиск и обновление котировок. Вне торгов новых сделок может не быть: сравнивать время самих цен

Состояние воркера и последний проверенный остаток: `GET /api/status` с Bearer-токеном сессии. Готовые разборы хранятся только в локальной БД: на другом компьютере их нужно выполнить заранее

Тесты без запросов к модели, из `backend` с активированным окружением:

```powershell
$env:RUN_DATABASE_TESTS = "1"
python -m pytest app/test_backend.py app/test_errors.py app/test_ranking.py app/test_profile_roles.py app/services/ai_agents/test_ai_agents.py -q
```

Проверки БД используют отдельную временную схему. Дополнительные интеграционные тесты агентов включаются `RUN_DB_INTEGRATION=1` и требуют права создания временной базы

Из `frontend`: `npm test`, затем `npm run build`

## После git pull

1. Установить зависимости заново, если изменились `requirements.txt` или `package-lock.json`
2. Сверить новые параметры `.env.example`, не перезаписывая свои секреты
3. Запустить `init_db.py`, затем перезапустить приложение

Окружение и базу заново создавать не требуется

## Ошибки запуска

- **Unresolved reference 'app'**: отметить `backend` как Sources Root, проверить интерпретатор
- **No module named …**: установить зависимости в окружение проекта
- **Ошибка PostgreSQL**: проверить службу в `services.msc`, подключение через pgAdmin и `DATABASE_URL`
- **Address already in use / Port 5173 is in use**: остановить предыдущий экземпляр процесса
- **Фронт не получает данные**: проверить `/health`, `VITE_API_URL`, CORS; повторить загрузку после старта API
- **Разбор недоступен / импорт остановлен**: проверить консоль процесса, ключ, лимиты и доступность шлюза; импорт повторить после устранения ошибки

## GitHub Pages

1. Разместить API и PostgreSQL на сервере с публичным HTTPS-адресом API
2. В серверном `API_CORS_ORIGINS` добавить origin Pages без пути репозитория, например `https://mishgite.github.io`, перезапустить API
3. **Settings → Secrets and variables → Actions → Variables**: добавить `VITE_API_URL` с HTTPS-адресом API без `/api`
4. **Settings → Pages → Source → GitHub Actions**
5. **Actions → Frontend · GitHub Pages → Run workflow**, выбрать ветку

Workflow публикует только `frontend/dist`. Все `VITE_*` публичные: ключей и паролей там быть не должно. Без доступного HTTPS API серверная версия приложения на Pages не работает

## Сервер: Docker и отдельный фронтенд

### 1. Подготовка сервера

Linux, Docker Engine и плагин Docker Compose v2: [установка Docker](https://docs.docker.com/engine/install/). Python и PostgreSQL на хосте не требуются

```bash
git clone https://github.com/Mishgite/Alpha_Hack_News_Analytics.git
cd Alpha_Hack_News_Analytics
cp docker/.env.example docker/.env
```

Использовать ветку с актуальной серверной конфигурацией. Все команды ниже выполняются из корня репозитория

### 2. Передача исходных данных

Эти файлы передаются отдельно от Git. На сервере нужна структура:

```text
backend/data/
  companies/
    df_Uid_data_hack.csv
    df_Fid_Uid_link_hack.csv
    df_Uid_payment_hack.csv
    selection.txt
  reports/
    *.pdf
  reports_processed/
    <папка каждого отчёта>/
      manifest.json
      page_*.json
```

`selection.txt` содержит ровно 50 ID из нашей выборки, по одному на строке. Нужны все 9 исходных PDF и JSON подготовки каждого отчёта с сохранением имён файлов и папок. PNG, TSV, TXT и исследовательские файлы для запуска не требуются

Архив на рабочем компьютере, из корня проекта в PowerShell:

```powershell
tar -czf "$env:USERPROFILE/Desktop/alfa-server-data.tar.gz" --exclude="*.png" --exclude="*.tsv" --exclude="*.txt" --exclude="*.md" -C backend/data reports reports_processed
```

Передать архив, три CSV и список ID компаний через SFTP/SCP. На сервере:

```bash
mkdir -p backend/data/companies
tar -xzf /path/to/alfa-server-data.tar.gz -C backend/data
cp /path/to/df_Uid_data_hack.csv backend/data/companies/
cp /path/to/df_Fid_Uid_link_hack.csv backend/data/companies/
cp /path/to/df_Uid_payment_hack.csv backend/data/companies/
cp /path/to/selection.txt backend/data/companies/
chmod -R a+rX backend/data/companies backend/data/reports backend/data/reports_processed
```

Путь `/path/to/` заменить папкой загрузки. Контейнер работает от UID 10001, поэтому входные файлы должны быть доступны ему для чтения

Новости с готовой разметкой уже включены в образ из `backend/data/examples/recent-news-2026-10-25.json`. Это сохранённые реальные новости с исходными датами, а не постоянно свежая лента. Новые новости собирает воркер

### 3. Настройки

В `docker/.env`:

- `POSTGRES_PASSWORD`: отдельный пароль контейнерной БД, в одинарных кавычках; URL-кодирование не требуется
- `LLM_API_KEY`: ключ команды, только на сервере
- `DATA_DIRECTORY=../backend/data`: путь относительно папки `docker`; можно заменить абсолютным серверным путём
- `FRONTEND_ORIGIN`: адрес фронта без пути, например `https://team.github.io`, а не `https://team.github.io/repository`
- `API_DOMAIN`: будущий домен API без протокола и пути, например `api.example.ru`
- `API_PORT=8000`: локальный порт API на сервере; наружу публикуется через HTTPS-прокси
- `LLM_DAILY_REQUEST_LIMIT=100`: общий лимит попыток API, импорта и воркера в этой БД
- `LLM_BUDGET_RESERVE_RUB=360`: остановка новых запросов при остатке 360 ₽; при бюджете 500 ₽ доступно около 140 ₽ с небольшим возможным превышением на последний запрос. Для обычной работы после проверок резерв можно изменить осознанно

Другие значения оставить из примера. Первый импорт получает признаки 50 компаний через модель и входит в эти лимиты. Если один ключ используется ещё на ноутбуке, расходы по ключу общие, а счётчики числа попыток в разных БД отдельные

```bash
chmod 600 docker/.env
docker compose --env-file docker/.env -f docker/compose.yaml config --quiet
```

`backend/app/.env` внутри образа отсутствует. Серверные настройки берутся только из `docker/.env`. Команда `config` без `--quiet` может вывести секреты

### 4. Первый запуск без публичного домена

```bash
docker compose --env-file docker/.env -f docker/compose.yaml up --build -d
docker compose --env-file docker/.env -f docker/compose.yaml logs -f bootstrap
```

Порядок: готовность PostgreSQL → создание схемы и тегов → проверка CSV, JSON и контрольных сумм PDF → отчёты и новости → 50 компаний и их признаки → API и воркер

Ожидается `Bootstrap complete: 50 companies, 104 news, 9 reports`. После этого `bootstrap` имеет состояние `Exited (0)`, остальные сервисы должны стать `healthy`:

```bash
docker compose --env-file docker/.env -f docker/compose.yaml ps -a
curl --fail http://127.0.0.1:8000/health
```

Выход из просмотра логов: Ctrl+C. Если импорт завершился ошибкой, исправить её причину и повторить `up -d`. Уже успешно размеченные компании не отправляются модели повторно. Автоповторы временных ошибок шлюза ограничены тремя на компанию; при ошибке данных, ключа или бюджета запуск останавливается

Пока домена нет, API доступен только на самом сервере. Для проверки с компьютера можно открыть SSH-туннель `ssh -L 8000:127.0.0.1:8000 user@server`, установить `FRONTEND_ORIGIN=http://127.0.0.1:5173` и запустить локальный фронт с `VITE_API_URL=http://127.0.0.1:8000`

### 5. HTTPS и размещение фронтенда

1. Создать DNS A-запись домена API на IP сервера; при наличии AAAA-записи IPv6 также должен вести на сервер
2. Открыть серверные порты 80 и 443; порт PostgreSQL наружу не публикуется
3. Указать реальные `API_DOMAIN` и `FRONTEND_ORIGIN` в `docker/.env`
4. Запустить прокси:

```bash
docker compose --env-file docker/.env -f docker/compose.yaml --profile https up --build -d
curl --fail https://api.example.ru/health
```

Caddy получает и продлевает сертификат автоматически при доступном домене и портах; сертификаты сохраняются в отдельном volume. [Требования Caddy к HTTPS](https://caddyserver.com/docs/automatic-https/)

5. В настройках GitHub Actions задать `VITE_API_URL=https://api.example.ru` и выполнить публикацию по разделу «GitHub Pages» выше. Для другого хостинга собрать фронт с этим же значением и разместить `frontend/dist`

Изменение `VITE_API_URL` требует новой сборки фронта. Изменение `docker/.env` требует `up -d`, одного `restart` недостаточно. На публичном фронте нельзя оставлять `127.0.0.1` или HTTP-адрес API

Текущий вход остаётся демонстрационным: пользователь выбирает компанию без банковской авторизации. Сервер рассчитан на показ хакатонного решения, реальные данные клиентов туда не загружаются

### 6. Повторный запуск и обновление

```bash
git pull
docker compose --env-file docker/.env -f docker/compose.yaml --profile https up --build -d
```

Без домена убрать `--profile https`. Если подготовка уже завершена, компании, реакции, новости и разборы сохраняются. Проверяются схема, исходные отчёты и контрольные суммы файлов. При изменении CSV, расшифровок PDF или версии их обработки пересчитываются платёжные признаки и связи выбранных компаний, обновляется индекс PDF. Неизменившаяся разметка сохраняется; эти операции не вызывают модель. Без изменений пересчёт пропускается. Существующая локальная БД Windows автоматически в контейнер не переносится

После перезагрузки сервера существующие контейнеры БД, API, воркера и прокси запускаются автоматически; API и воркер ждут доступности БД. При изменении структуры таблиц неподдерживаемая схема останавливает подготовку, автоматических миграций нет

Данные БД находятся в `alfa-news_postgres-data`, отчёты импорта и общие примеры ошибок разметки в `alfa-news_app-runtime`. Команда `down` сохраняет эти volumes; `down -v` удаляет БД, её нельзя использовать для обычного обновления

Резервная копия БД, из Linux-терминала:

```bash
docker compose --env-file docker/.env -f docker/compose.yaml exec -T database sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' > alfa-news.dump
```

Исходные PDF, CSV и JSON сохранять вместе с резервной копией отдельно. Смена `POSTGRES_PASSWORD` в `.env` не меняет пароль уже созданной роли PostgreSQL: сначала изменить пароль роли в БД, затем обновить `.env`

### Воркер и диагностика

Источники и интервалы задаются в `docker/worker.json`; после изменения перезапустить воркер. По умолчанию включены RSS Банка России, экономические рубрики ТАСС и Интерфакса, котировки MOEX. Дополнительные RSS перечисляются в `sources`, формат тот же, что в разделе «Что выполняет воркер»

```bash
docker compose --env-file docker/.env -f docker/compose.yaml logs --tail 100 bootstrap api worker
docker compose --env-file docker/.env -f docker/compose.yaml restart worker
```

Без воркера: `up --build -d api`; если воркер уже запущен, отдельно `stop worker`. Новые разборы и сбор новостей тогда не выполняются. Уточняющие вопросы к готовым разборам остаются платными вызовами API

Дополнительный универсальный парсер не нужен для первоначальной загрузки: подготовленные отчёты уже импортирует `bootstrap`. В Docker он читает папку `reports` и всегда сохраняет оригиналы; OCR-зависимости устанавливаются только в его отдельный образ

```bash
docker compose --env-file docker/.env -f docker/compose.yaml --profile ingest run --build --rm parser
```


## Проверки и обновление контекста

После получения изменений запустить `app/infrastructure/database/init_db.py` через PyCharm: существующие данные сохраняются, добавляются новые служебные таблицы

Из `backend`, с выбранным окружением:

```powershell
python app/refresh_company_context.py
python app/evaluate.py --database
python app/monitor.py --check
```

Первая команда обновляет агрегаты платежей и связей для выбранных 50 компаний. Вторая сохраняет отчёт качества в `data/evaluation`. Третья проверяет текущие предупреждения. Все три команды работают без платных запросов к модели. [Метрики и правила оценки](quality.md)

В Docker, из папки `docker`:

```bash
docker compose exec api python -m app.container refresh-context
docker compose exec api python -m app.container evaluate --database
docker compose exec api python -m app.container monitor --check
```

Отчёты оценки в Docker: `/workspace/runtime/evaluation`, volume `app-runtime`

## Комплект для сдачи

Из `backend`:

```powershell
python app/prepare_submission.py
```

Результат: `backend/data/submission/<время>/`

- `source.zip`: рабочая версия кода, инструкции, публичная подборка новостей
- `private-data.zip`: три исходных CSV, `selection.txt` с 50 ID, исходные PDF, подготовленные страницы JSON и ручные исправления распознавания
- `archives.json`: контрольные суммы архивов
- `START.md`: порядок распаковки и запуска

`.env`, ключи, окружение Python, зависимости фронта, исследования и локальный `app/main.py` в комплект не включаются. Архив данных не публикуется в Git

На другом компьютере:

1. Распаковать `source.zip` в папку проекта
2. Распаковать `private-data.zip` в `backend/data`
3. Создать `docker/.env` по `docker/.env.example`, заполнить пароль БД и выданный ключ модели
4. Указать `FRONTEND_ORIGIN`; для HTTPS также `API_DOMAIN`
5. Запустить `docker compose up -d --build` из `docker`
6. Проверить `docker compose logs bootstrap` и `docker compose ps`
7. Собрать фронт с адресом API по разделу выше

Первый запуск создаёт БД, импортирует выбранные компании, размечает их моделью, загружает новости и PDF. Запросы разметки ограничены настройками бюджета. При исчерпании лимита импорт можно продолжить после сброса лимита; готовые профили повторно не размечаются. Следующие запуски используют сохранённый volume БД

Компоненты: `database` (PostgreSQL), `bootstrap` (инициализация), `api`, `worker`; `proxy` (Caddy, профиль `https`), `parser` (дополнительный импорт, профиль `ingest`). Фронт собирается и размещается отдельно

### Повторная подготовка PDF

Для обычного запуска достаточно готовых `reports_processed` из закрытого архива. Для повторного OCR:

1. Установить Tesseract с русским и английским языками
2. Из `backend` установить дополнительные зависимости:

```powershell
python -m pip install -r app/requirements-ocr.txt
python app/prepare_reports.py
```

Скрипт читает `data/reports` и `data/report_annotations.json`, сохраняет результат в `data/reports_processed`. Если Tesseract отсутствует в PATH, передать `--tesseract ПУТЬ_К_TESSERACT`. Модели OCR сохраняются в `data/ocr_models`; их контрольные суммы и параметры записываются в манифесты. После обработки перезапустить воркер для импорта исправленного текста
