# Проверка фронтенда и бэкенда

Дата: 25.10.2026. Ветка: `dev-dasha_1`.

Основания: исходный кейс «Альфа Хак — Новостная аналитика», внутренние `ALFA_NEWS_TECHNICAL_SPEC.md` и `ALFA_NEWS_TWO_RANKING_OPTIONS-3.md`, конспект ответов `Defense_Guide_Alpha_Hack_2026.docx`. Конспект различает требования, разъяснения и рекомендации; его рекомендации не считаются обязательными правилами. Оригиналы не изменены.

## Что проверено

- Контракты входа, каталога компаний, профиля, интересов, ленты, пагинации, реакций, замечаний к тегам, заданий AI, разборов, истории вопросов, PDF и биржи
- Формула работает без LLM при чтении ленты; роль влияет на приоритеты, разбор кешируется по компании и новости
- Планирование агента, поиск банковской аналитики, проверка доказательств, ограниченная коррекция и сохранение трассы реализованы на бэке
- 74 проверки бэка и 5 subtests прошли без пропусков, включая отдельную временную БД для проверки создания схемы и изолированную схему для сервисов
- 11 проверок фронта прошли, production-сборка проходит
- В браузере с настоящим API проверены сохранённый разбор, точные цитаты, снимок признаков компании и карта рынка
- В рабочую БД загружены 100 [реальных публикаций](news-examples.md) за 19–25 октября из 18 источников. У региональных событий отмечены 24 региона РФ, также есть федеральные и зарубежные новости. Через TestClient с рабочей БД проверены все 100 ответов чтения новости и шесть страниц ленты; все записи подборки присутствуют, повторный импорт сохраняет ID и количество записей
- Проверены живая RSS-лента ЦБ, обновление котировок и цикл API → очередь → worker → модель → БД → API на новости о порте Корсаков. Разбор частичный: подтверждённой позиции банка по этому событию нет. Повторный запрос использовал кеш
- Разметка подборки и новый разбор потребовали 10 обращений к модели, расход по шлюзу увеличился примерно на 5,25 ₽. Общий расход за 25 октября на момент проверки около 9,09 ₽ из разрешённых 100 ₽ на проверки
- Эти расходы относятся к первым семи примерам и прежней проверке разбора. Дополнительные 93 публикации пересказаны и размечены ассистентом без API модели: счётчик LLM до и после загрузки равен 29. Показов, открытий и реакций при проверке API не создавали

## Исправлено

- Ссылка у утверждения открывает его `evidence_quotes`, а не общий текст источника
- Кнопка признаков показывает `company_feature_refs` конкретного утверждения из исторического снимка. Добавлен `GET /api/analyses/{id}/context`; чужая компания получает 403, изменение текущего профиля не переписывает снимок
- Просроченная лента обновляется при повторном открытии
- Пока сохраняется реакция, обе кнопки заблокированы; запоздалый ответ не изменяет другую страницу
- История вопросов не затирается ответом от предыдущего экрана; сохраняется при обновлении настроек профиля
- Проверка трассы различает корректную структуру и подтверждённость выводов
- Кредитный признак в карточке читается и из `CL_PRODUCT_LOA_MARK`, а не только из производных факторов
- Площадь прямоугольников биржи пропорциональна обороту; проверены границы, отсутствие пересечений и нулевые значения
- Добавлен [перечень сторонних компонентов](../THIRD_PARTY_NOTICES.md)
- Исправлены два кратких изложения в подборке: доступные подключения и предполагаемый оператор больше не описываются как выполненные действия. Инструкция разметчика уточнена, версия разметки изменена

Локальный предел `LLM_DAILY_REQUEST_LIMIT` независим от денежного бюджета. На момент проверки использовано 29 из 30 вызовов: до сброса лимита в 00:00 UTC новые многошаговые разборы могут быть остановлены защитой. Чтение ленты, импорт готовой подборки и чтение сохранённых разборов LLM не требуют

## Что ещё нужно

1. **Платёжные связи и группа.** Импорт компаний читает `df_Uid_data_hack.csv`, но отдельного импорта платежей и связей физлиц в рабочий сценарий нет. `GROUP_ID` хранится, однако анализ группы и концентрации платежей в агент не подключён. Нужны агрегаты с периодом и ограничениями выборки; они не должны объявляться долей рынка
2. **Дубли разных источников.** БД устраняет повтор внутри источника по ID/URL. В рабочем цикле воркера нет общего объединения одинаковых и близких текстов из разных источников с сохранением всех ссылок. Парсер в этой проверке не менялся
3. **Оценка качества.** Нет завершённого отчёта на отложенных новостях с несколькими компаниями: релевантность топа, подтверждённость выводов, качество цитат, персонализация, время и стоимость. Технические тесты и один реальный разбор такую оценку не заменяют
4. **Подготовка сдачи.** В исходном кейсе, стр. 8, указаны Docker-конфигурация, README, фиксация версии и воспроизводимый запуск. Docker и общий README отсутствуют по прежнему решению команды; есть отдельные инструкции бэка и фронта. Проверка установки на чистом компьютере ещё нужна
5. **Работа через интернет.** GitHub Pages размещает фронтенд; публичного HTTPS API нет. После размещения бэка нужны CORS, проверка API/воркера с опубликованного сайта и доступ жюри к репозиторию. Предоставленные CSV/PDF нельзя публиковать вместе с фронтом

## Отличия от внутреннего плана

- Bearer-сессия вместо cookie, маршруты `/api` вместо `/api/v1`; фронт и бэк согласованы между собой
- Vite и JavaScript вместо упомянутого в раннем документе React
- Рекомендации пока формулой, по последнему решению команды; ML не подключён
- Допустимы новости без уверенно определённых тегов, вместо выдуманного обязательного тега
- Замечания к тегам сохраняются в БД, но ещё не проходят проверку и автоматический перенос в `bad_news.json`; подтверждённые ошибки пока добавляются отдельно
- Фильтр эмитентов «Связано с моей компанией» отключён как запланированное расширение

Это проверка текущих сценариев и известных ошибок, а не доказательство отсутствия всех возможных ошибок или полного качества аналитики.
